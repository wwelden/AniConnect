# AniConnect requirements

## Goal

Be the best MCP server for managing an AniList anime list: the one where a plain-language request ("I watched episode 3 of JJK", "rate the second season of Spy x Family an 8") changes the right entry, in one step, without the user ever seeing an ID.

"Better" is measured, not claimed: the eval suite (R6) scores us and the alternatives on the same requests.

## Baseline: existing AniList MCP servers

Surveyed 2026-11-16 from their READMEs (not yet run by us).

| | [yuna0x0/anilist-mcp](https://github.com/yuna0x0/anilist-mcp) | [gavxm/ani-mcp](https://www.npmjs.com/package/ani-mcp) |
|---|---|---|
| Tools | ~44, thin wrappers over the API | 52, incl. taste profiles, picks, analytics |
| Identifying a show | AniList ID | AniList ID |
| List writes | generic add / update / remove | progress, rate, add, delete, undo, batch (dry-run) |
| Auth | paste a token into config | paste a token into config |
| Transport | stdio, HTTP | stdio, HTTP |

Where we aim to win: name and season resolution (R1), a small and accurate tool set (R2), hosted sign-in that works in claude.ai and on mobile (R7), and evidence (R6).

### R1: Name and season resolution

Every tool that targets a show accepts a title (or an ID, or the show's anilist.co link) and picks the right AniList entry itself. A number is always an ID; a string of digits is a title when a show is titled that way ("86"), otherwise an ID. A link (`https://anilist.co/anime/154587/...`, or `/manga/`) is its ID. A manga is named the same ways (R0.17).

| ID | Requirement | Status |
|---|---|---|
| R1.1 | Match any title form: English, romaji, native, AniList synonyms, common acronyms (JJK, AoT, MHA), ignoring case, punctuation and accents. | Done (resolver tests) |
| R1.2 | Tolerate small typos ("frieran"), and resolve them as the right spelling would be. A name that matches only listed shows, with a letter or two off, is first searched as written (it may be a real title one letter off a listed one: "kaiji" beside Kaiju No. 8); if nothing matches better, it is respelled from those shows' titles and resolved again, so an episode of "frieran" after finishing season 1 goes to season 2, as for "frieren" (R1.4), and "narto" with only Shippuden listed asks, as "naruto" does (R1.3). When listed shows would respell a word differently, it isn't respelled and resolves as before. One AniList search more, only on the typo path. | Done (resolver tests; a generated test misspells every title on the test persona's list) |
| R1.3 | Prefer shows already on the user's list over the rest of AniList, except over a show titled exactly as asked: changing the status or score of "Naruto" with only Shippuden on the list asks which one, and "Jujutsu Kaisen" with only the JJK 0 movie listed is the series. ### R5: Reliability

| ID | Requirement | Status |
|---|---|---|
| R5.1 | Handle AniList's rate limit (30 requests/minute, per the live API's `x-ratelimit-limit`) by reporting the wait, never retry-looping. | Done: one limiter shared by every client in the process (each sign-in on the hosted server) keeps requests under the limit in a sliding minute, first come first served, except that while another user (AniList account) has a request in the window, one user holds at most half of it, so one user's import can't take a whole minute from another (a user alone has the whole limit); it follows AniList's `X-RateLimit-Limit` (`X-RateLimit-Remaining` isn't used: it can't say when requests from another app on the IP leave AniList's window). A request waits up to 30 seconds for a slot, and a tool call's waits all end within 40 seconds of the call starting (`CALL_WAIT_MS`), so a call of several requests still answers within a minute; a request further off isn't sent, and the wait is reported. A 429 pauses every client for its `Retry-After` (else `X-RateLimit-Reset`, else a minute), and the request, which gives its slot back, is sent once more if that fits the same bounds (a rate-limited request isn't run, so this is safe for writes too); a second limit is reported. This keeps a large `update_shows` call from failing its last few shows. Reads that fail with a 5xx or a network error are sent once more after a second; writes never are (the change may have been saved), and nor are timeouts (a second 15-second wait would take most of a tool call's minute). Requests per tool call are unchanged |
| R5.2 | Stay within a few AniList requests per tool call. | Done (1–2 typical while the list is cached (R5.4), one more for a change made over 5 seconds after the list was fetched, 3–4 when it is fetched. Season lookups walk the sequel chain through the search results, which carry relations, and fetch any seasons search missed two per request: "the new season of my hero academia" takes list, search and write, down from 9) |
| R5.3 | Work with large lists (1,000+ entries). | Done: measured 2026-11-17 on a public 2,752-entry list, AniList returns the whole list in one request (2 MB, 1.6 s), where pages of 500 would take 6 requests of the 30 a minute, so the list stays one unpaged request. `search_my_list` pages over that list with `offset` (each page is cut from the cached list, refetched after its 60 s TTL), so every entry in a status can be read. Resolving a name over it takes 25–80 ms; a test holds 3,000 entries to the same answers |
| R5.4 | Cache the user's list briefly and refresh it after writes, to cut AniList requests (needed once hosted, where the rate limit is shared per IP). | Done: the list is reused for 60 seconds; our own writes and deletes patch it, so a read after a write is never stale; changes made elsewhere show up once it expires. A write reads its show again first (`update_shows`: all its shows in one request) when the list is more than 5 seconds old, so it never plans from a value changed elsewhere. The hosted server's users share one rate limiter (R5.1), so one user's burst waits its turn instead of sending everyone into a 429 |
| R5.5 | Warn before the AniList token expires: read the expiry from the token (a JWT) with no request, add a one-line warning with the date and renewal steps to tool results in the last 14 days (on the first call of each server process, then at most once a day), and once expired fail without calling AniList. Tokens that can't be decoded behave as before. | Done |

## Non-goals (for now)

- Manga beyond the list tools (R0.17): searching AniList for manga, reading history and "what's next" for manga.
- Social features (activity posts, follows, threads). Favorites are supported (R0.18).
- Taste profiling, picks of our own and stats. ani-mcp already covers these; we would need a clear edge to compete here. Recommendations come only as AniList users make them, for one show (R0.16): the edge is taking the show by name and season and checking each against the user's list, which ani-mcp's recommendation tools don't.
- Importing from MyAnimeList or Kitsu.
